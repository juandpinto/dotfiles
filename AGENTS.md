# AGENTS.md

Personal macOS and Omarchy dotfiles repo for Juan Pinto. The existing root
Stow package remains the Mac deployment; Linux-only files live in the ignored
`platforms/omarchy/home/` overlay. Neovim, IPython and Yazi are shared. No CI pipeline.
Configuration validation and Linux migration notes live in `platforms/omarchy/`.

## Symlink model (GNU Stow)

- Setup is **GNU Stow**: this whole repo is stowed as a single package into
  `$HOME` (`stow -t ~ .` from here, or equivalent). `.stow-local-ignore` at
  the repo root excludes `.git`, `.gitignore`, `.DS_Store`, and the
  top-level `README.md`/`AGENTS.md`/`package-lock.json` from being linked.
  The legacy Mac package still has no build or CI step beyond running Stow. Linux has a selective linker and narrow configuration regression checks under `platforms/omarchy/`.
- Top-level dotfiles are symlinked directly: `~/.zshrc`, `~/.wezterm.lua`
  -> `~/.dotfiles/<file>`.
- Stow "folds" a directory into a single symlink only when the target
  doesn't already exist as a real directory, e.g.
  `~/.config/nvim -> ../.dotfiles/.config/nvim`. Where the target already
  existed as a real directory before stowing (e.g. `~/.config/pi/agent`,
  which the `pi` CLI itself populates with runtime state like `auth.json`
  and `sessions/`), Stow can't replace it with one symlink and instead
  descends and links the individual files/subdirs inside
  (`~/.config/pi/agent/AGENTS.md -> ../../../.dotfiles/.config/pi/agent/AGENTS.md`,
  etc.). That's normal Stow tree-folding, not a sign of manual/partial
  linking — but it does mean a new file added under an already-real target
  directory won't be linked until `stow` is re-run (it won't auto-adopt new
  files into an existing fold on its own in all cases, so re-run `stow -t ~
  .` after adding files there).
- `.config/pi/agent/npm/` and `.config/pi/agent/git/` are **not** in this
  repo at all (gitignored, never stowed) — they're pi's own package-install
  dirs (`npm install`/`git clone` targets for whatever's listed in
  `settings.json`'s `packages` array), fully regenerated by pi itself on
  startup from that array. They used to live inside this repo and get
  symlinked through like everything else, but pi's package installer has a
  path-resolution bug that corrupts `npm/package-lock.json` with runaway
  `.dotfiles/.dotfiles/...` nesting when that directory sits behind a
  symlink boundary (confirmed: plain manual `npm install`/`uninstall` in the
  same dir doesn't reproduce it; only pi's own reconcile-on-startup path
  does). Moving them out to be plain real directories under
  `~/.config/pi/agent/` removes the symlink boundary entirely, so the bug
  can't trigger. `settings.json`'s `packages` array (still tracked/symlinked)
  remains the actual source of truth — on a fresh machine, stow the repo as
  usual and pi installs `npm:`/`git:` packages into fresh local dirs on
  first run, no manual steps needed.

## Incremental dual-OS deployment

- Keep one `main` branch, not permanently diverging OS branches.
- **Do not run the root `stow -t ~ .` on Linux.** It also contains AeroSpace,
  Sketchybar, launchd, Karabiner, and macOS shell/terminal settings.
- Both Linux and macOS use `~/.dotfiles`. Prefer `$DOTFILES_DIR` or relative links in new code, not a username or a platform-specific checkout path.
- Linux's active Pi agent directory remains the real `~/.pi/agent`, with individual authored resources linked from `.config/pi/agent` and Linux settings from the overlay. Preserve the distro skills and never link credentials, sessions, model caches, npm or git package installations into this repository. On Linux, Omarchy's existing theme-set hook publishes our exact Everforest palette to the generated `~/.pi/agent/themes/everforest-omarchy.json`; Pi's native file watcher reloads it. Do not restore terminal-detected light/dark pairing or add another watcher—the Herdr notification/color-query race can leave Pi on the wrong palette. The Mac's theme-following package remains unchanged.
- Linux links only explicitly selected shared configs and files under
  `platforms/omarchy/home/`. The overlay is excluded from root Stow, so it
  cannot accidentally become a `~/platforms` directory on the Mac.
- Herdr is shared by both machines: `.config/herdr/config.toml` (tmux-style
  keys, Everforest light/dark overrides) and the `.config/herdr/lastfocus/`
  and `.config/herdr/labels/` plugins. `~/.config/herdr` is Herdr's runtime
  directory, so only those three entries are linked into it (Stow on the Mac,
  `link.sh` on Linux), and each plugin is registered by path once per machine
  with `herdr plugin link ~/.dotfiles/.config/herdr/<plugin>`. See their READMEs.
- The four mail account configs (`aerc/accounts.conf`, `isyncrc`, `msmtp/config`, `notmuch/default/config`) contain email addresses and logins, so they live in the **private companion repo** `~/.dotfiles-private` (same `omarchy/home/` layout; `DOTFILES_PRIVATE_DIR` overrides the path), never in this public repo. `link.sh` links them when present; `.gitignore` blocks their public paths. Keep docs here free of real addresses too (use `<icloud-login>`-style placeholders).
- `link.sh` walks overlay roots with `find` (so uncommitted authored files still link) but prunes `__pycache__`/`.git`. Directory links, not per-file links: Omarchy theme dirs, our `jdpinto.*` plugin clones, Keystroke extensions, and `~/.config/kanata`. Everything else links file by file so real directories (`~/.config/aerc`, `~/.config/hypr`, `~/.local/share/applications`) can mix our links with Omarchy-managed files.
- Never hardcode `/home/<user>` in overlay files; use `os.getenv("HOME")` in Hyprland Lua and `$HOME`/`%h` elsewhere (strata's installer once wrote absolute paths into `bindings.lua`; they were replaced).
- Shared Neovim/IPython edits must retain Mac behavior. Omarchy owns desktop
  palette selection; its theme-set hook writes the same `~/.cache/appearance`
  contract that launchd supplies on macOS. No second Linux polling daemon.
- Do not link runtime data, credentials, histories, Jupyter connection files,
  or generated theme files into this repo. Backups stay under local state.
- Do not push or commit the migration without user review.

## Copilot CLI mirror of the pi setup

- pi isn't approved on the work Mac yet, so `.copilot/` (Mac root Stow only) points Copilot CLI at the pi global instructions and skills instead of copying them: `copilot-instructions.md` and `skills` are relative symlinks to `.config/pi/agent/AGENTS.md` and `.config/pi/agent/skills`. Edit the pi originals; never fork Copilot-specific copies.
- `.copilot/extensions/pi-prompt/extension.mjs` trims Copilot's system prompt and tools to roughly pi's size through the SDK's `systemMessage` customize mode (`SystemMessageSection` in the bundled `copilot-sdk/types.d.ts`). It only loads with `experimental: true`. Copilot uses a different prompt template and editing tools per model family (`edit`/`create` for Claude, `apply_patch` for GPT-5), and puts model-specific guidance in `runtime_instructions`, which also carries runtime context, so the extension drops guidance blocks by name. A malformed configuration makes Copilot refuse every prompt rather than ignore the extension, so run `tests/test_copilot_prompt.mjs` after changing it. The test runs Copilot offline against a fake model, once per model family, and needs no account.
- `~/.copilot` and `~/.copilot/extensions` are Copilot's runtime directories and must stay real, so Stow links only our entries into them. `settings.json` is never tracked, because it stores trusted folders. `.gitignore` admits only our entries under `/.copilot/`.
- Running `copilot` on Linux goes through Omarchy's mise wrapper, which runs `mise use -g copilot` and so edits the linked `platforms/omarchy/home/.config/mise/config.toml`. Revert that if it was unintended, or call the binary under `~/.local/share/mise/installs/copilot/` directly.

  Plugin pins live in `.config/nvim/nvim-pack-lock.json`.
- Entry point is `.config/nvim/init.lua`, which wires up
  `lua/options.lua`, `lua/keymaps.lua`, `lua/pack.lua`, and `lua/plugins.lua`

  repo's Lua files.

## Auto dark/light mode syncing

- `bin/appearance-watcher.sh` is the **single source of truth** for "is
  macOS in dark or light mode right now". It's the consolidation of what
  used to be four independent tools (sketchybar, tmux, btop, nvim) each
  running their own `defaults read -g AppleInterfaceStyle` polling loop on
  a different interval — same detection repeated four times, with
  inconsistent lifecycle management (pidfile locks, `nohup`, tied to
  whichever app happened to launch it).
- It runs as a LaunchAgent
  (`Library/LaunchAgents/com.juanpinto.appearance-watcher.plist`, stowed
  into the real, pre-existing `~/Library/LaunchAgents/` the same way
  `~/.config/pi/agent` tree-folds — other apps' plists live there too, e.g.
  sketchybar's own brew-managed one), so it's one long-lived,
  auto-restarting process (`KeepAlive` + `RunAtLoad`) instead of scripts
  bootstrapped ad hoc from each tool's own config.
- On every detected change it writes `dark`/`light` to `~/.cache/appearance`
  (untracked — pure runtime state, not meant to be versioned) and reacts
  directly for tools that don't have their own way to pick up a live
  change. Logs go to `~/Library/Logs/appearance-watcher.{out,err}.log`.
- The plist's `ProgramArguments` invokes `/bin/bash -c 'exec
  "$HOME/.dotfiles/bin/appearance-watcher.sh" >> ... 2>> ...'` rather than a
  literal absolute path, and deliberately has no `StandardOutPath`/
  `StandardErrorPath` keys (those don't expand `$HOME` or any other
  variable, so they'd have to hardcode a username). This keeps the plist
  portable across machines with different usernames sharing this same repo
  — confirmed launchd sets `$HOME`/`$USER` correctly for GUI-domain agents
  even without them in `EnvironmentVariables`. Don't hardcode `/Users/<name>`
  anywhere in this plist again; a previous version did and the agent
  silently failed to load on any machine whose username didn't match,
  which broke nvim's appearance sync (see `everforest.lua`) since
  `~/.cache/appearance` was never created.
- **To add auto-dark-mode support to a new tool**, first figure out which
  category it falls into, since each needs a different integration in
  `react()` in `bin/appearance-watcher.sh` (or, for nvim-like cases, its own
  config):
  1. **Tool re-derives its own colors fresh on reload/restart** (sketchybar,
     tmux): just trigger that reload/restart from `react()`. No shared
     state needed — the one-shot `defaults read` each already does at its
     own load time is fine as-is, it just needs to be re-triggered on
     change instead of continuously repeated.
  2. **Tool only reads a persisted config value passively on startup, with
     no live-reload hook of its own** (btop): `react()` must rewrite that
     config value **unconditionally** — not gated on whether the tool is
     currently running — so a fresh launch later still picks up the right
     theme. Only gate the *live* reload signal (e.g. a `SIGUSR2`-style hot
     reload) on the process actually existing.
  3. **Tool is a long-running scriptable process that can read a file
     itself** (nvim, see `.config/nvim/lua/plugins/everforest.lua`): have
     it read `~/.cache/appearance` directly instead of re-invoking
     `defaults read` — a plain file read is far cheaper than spawning a
     subprocess on a timer, and keeps it on the same single detection point
     as everything else. Pair a lightweight polling timer (as a background
     safety net) with a focus/refocus event (`FocusGained` for nvim, which
     requires `focus-events on` in `tmux.conf` — already set via the
     `tmux-sensible` plugin) as a guaranteed correction point: without it, a
     change that happens while the tool is unfocused/backgrounded can sit
     uncorrected until the next poll tick.
- **Not** wired into this: pi's own theme-following
  (`npm:@mjakl/pi-dark-or-light` in `.config/pi/agent/settings.json`). It's
  a separate Node/TS extension ecosystem with its own well-designed
  detection chain (native macOS `osascript` first, then tmux's own
  `#{client_theme}`, `DARK_MODE` env, OSC 11, `COLORFGBG`) — bridging it to
  read the shared state file would mean patching a third-party package, and
  the effort wasn't worth it given it already works reliably on its own.
- Debugging: `launchctl list | grep appearance-watcher` for status; after
  editing the script, restart it with `launchctl bootout
  gui/$(id -u)/com.juanpinto.appearance-watcher` followed by `launchctl
  bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.juanpinto.appearance-watcher.plist`.
